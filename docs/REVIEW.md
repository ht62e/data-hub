# 設計整理と実装レビュー

新規システムとして現在の要求を優先し、後方互換性用のAPIや設定は維持していません。対象はハブ、DAG、取得契約、プロバイダ、負荷制御、通信層、SDK、設定とテストです。

## 解消した複雑さ

今回の整理では、ハブの各RPCに散在していた例外変換を `RpcErrorInterceptor` に集約しました。
サービスは要求をCoordinatorへ渡し、境界で扱う必要がある例外だけを変換します。
上流の `RpcException` とサイズ・容量分類のトレーラーはそのまま伝播し、未知の実装例外は
gRPC標準のエラー処理へ渡します。すべての障害をUnavailableへ変換する処理は削除しました。

登録情報とgRPC接続の管理は、通常のDictionaryと短いロックへ変更しました。
登録競合の判定・更新・失効削除を同じロック内で完結させ、ConcurrentDictionaryの更新
デリゲートや条件付き削除、接続生成用のLazyを不要にしています。

プロバイダの `Program.cs` は起動設定に絞り、取得アダプタを `LogSources.cs`、
取得サービスを `ProviderService.cs`、リース更新を `RegistrationWorker.cs` へ分離しました。
起動時に検証した登録内容を変更不可の `ProviderRegistration` として共有し、登録要求と
取得時の識別照合がずれることを防ぎます。登録要求と接続先は更新ループの外で一度組み立てます。
起動時に配置に応じた登録クライアントを1個構築します。外部ノードは登録先URLと専用キーだけで接続できます。
リース更新とDAG再検証は、それぞれ1回の試行に対して次の待機時間を決めます。ホスト停止時にはRPCと待機の両方にキャンセルを伝播します。

読み取りは.NET標準の `ConcurrencyLimiter` から許可を1件取得し、処理終了時に解放します。同時実行は1件、待機は `MaxPendingReads` 件までです。従来の2個のセマフォと手動の解放処理を削除しました。下流のないハブの探索は、登録簿が既に整列したローカル一覧をそのまま返せるため、カタログの再統合と再ソートを省いています。

| 対象 | 現在の設計 |
| --- | --- |
| 転送モード | クライアント指定を削除。MSAプロバイダへはMSA経由、外部プロバイダへは所有ハブ経由で取得する |
| 接続先 | ProviderTargetのoneofでMSAサービス／外部ノードを表現。内部モデルはProviderAddress。複数URLや配置種別との不整合を避ける |
| 外部ノード | 物理URL・キーは所有ハブだけのExternalNodes設定。入口ハブとSDKには不要 |
| ハブ間中継 | 所有ハブをMSA論理名で直接呼ぶ。DAGの中間ハブは経由せず、中継先はローカル登録のみ取得する |
| REST一覧 | `GET /api/sources` に一覧と探索状態を統合。重複APIと状態ヘッダーを削除 |
| REST取得 | `GET /api/records` にsourceIdと件数を渡す。選択状態はクライアントが保持する |
| ソースID | ローカル・遠隔とも `所有ハブID/ローカルソースID` に統一。短縮IDとの分岐と重複した公開ID項目を削除 |
| 物理URL | 登録・カタログから削除。MSA接続先は共通通信層、外部接続先は所有ハブの設定に集約 |
| プロバイダAPI | 取得はgRPCのみ。不要な診断用REST APIを削除 |
| 登録競合 | 有効なリースと異なる接続先からの登録を原子的に拒否。同じ接続先の更新と失効後の引継ぎを許可 |
| 待機上限 | 実行中1件と設定された待機枠だけを受け付け、キャンセル・取得失敗時にも枠を解放 |
| サイズ上限 | protobufのレコード・応答バイト数を読込中に検査。超過時は明示的なエラーとして返す |
| 選択状態 | SDKはインスタンスごとにソースIDを保持し、RESTクライアントは取得ごとにIDを送る |
| SDK取得 | 入口ハブのHubApi.Readに統一。SDKの接続先設定は入口ハブのみ |

外部ノードへの到達性は「所有ハブまたはそのプラットフォームから接続できる」という条件に合わせています。単一ハブと連結ハブで同じ処理を使い、所有ハブが入口自身なら余分なハブ間通信を行いません。

## 責務と依存関係

- `HubCoordinator`：要求されたソースの解決、取得前のポリシー評価、転送、監査。クライアントの接続方法はREST／gRPCで区別する。
- `ReadOptions`：取得期限の設定と計算。呼出元の短い期限を引き継ぎ、DAG通信への期限管理の依存を取り除く。
- `DataHubClient`：SDKインスタンス内に選択したソースIDを保持し、取得ごとに入口ハブへ送る。
- `IProviderReader / GrpcProviderReader`：MSAプロバイダ、自ハブの外部ノード、遠隔ハブの外部ノードへの転送。
- `FederationNetwork`：DAGのRPCと探索期限、通信障害、確認済み構成と接続状態の管理。
- `FederationTopologyValidator / FederationCatalogMerger`：副作用のないDAG検証とカタログ統合。
- `SourceDescriptor / DiscoveredSource / SourceCatalog`：変更不可の内部情報。`SourceMappings` がprotobufとの変換・受信検証を担当する。
- `IPlatformGrpcClientFactory`：MSAの名前解決と配送。独自基盤の共通クライアントに差し替える。
- `ExternalNodeClients`：所有ハブの外部ノード接続。`GrpcConnections` が開発用の接続再利用と宛先認証を担当する。
- `ReadPayloadLimits`：非同期列挙されたレコードから、サイズ予算内のReadReplyを組み立てる。アダプタは配列全体をメモリへ蓄積しない。
- `RpcErrorInterceptor`：ハブの全Unary RPCでアプリケーション例外を一度だけgRPCへ変換する。想定外の例外は捕捉しない。
- `ProviderRegistration`：プロバイダの登録内容を起動時に固定し、リース更新と取得時の照合で共有する。

登録時の接続先は `ProviderAddress.IsValid` で直接検証します。検証のためにprotobufへ変換せず、変換は登録・通信の境界で行います。

検証後の分岐障害では、確認済み構成を保持したDegraded状態で健全な分岐の探索・取得を続けます。各探索RPCで照合する起動識別子は、その送信元ハブが検証した直下の相手のものです。初回の遠隔連結には到達範囲全体の検証が必要です。

新しいプロジェクトや外部パッケージは追加していません。通信層プロジェクトからContractsへの参照を追加し、プロバイダの論理的な接続先の変換を共通化しました。単純な検証・統合・設定処理にはインターフェースを増やしていません。

3系統のテストは成功しています。実際のMSA、PostgreSQL、高負荷・長時間運転は未検証です。ローカル結合テストは、実ネットワークの到達制限や認証基盤を再現するものではありません。

資源制限の回帰試験では、登録の同時競合と失効後の引継ぎ、待機枠の超過・キャンセル・失敗後の回復、protobufバイト境界と列挙中止を確認しました。単一ハブ結合試験で、protobufの上限内でもJSONエスケープによりREST応答が上限値を超えるデータの取得、登録AlreadyExists、単一・複数レコードのサイズ超過と回復を確認し、連結ハブでもサイズ超過分類がSDK／REST 422まで伝わることを確認しました。

今回追加した回帰試験は、共通gRPC境界のエラー分類、上流エラー・トレーラーの保持、
未知の例外の非変換、登録の失効清掃とスナップショット保持、監視通信の失敗・タイムアウト・
キャンセルを対象にしています。単一ハブではJSON構文エラーと `[null]` の両方がgRPC Unavailable／REST 503になり、ファイル修復後に取得が回復することを確認しました。外部プロバイダは使用しないMSAの接続設定が不正でも登録・取得に成功します。

## 今回の選択と取得の設計

ハブは取得ごとにソースIDを受け取り、探索、ポリシー評価、取得を行います。クライアント別の選択表、期限、容量制限、定期清掃、選択変更の競合検出を削除しました。SDKは選択をインスタンス内に保持し、取得開始時にIDを確定します。存在確認やポリシーによる拒否は取得時に行います。

SDKの取得は入口ハブへ統一したため、SDKに必要な接続先は入口ハブだけです。MSAプロバイダの応答本体も入口ハブを通るため、実運用では入口の帯域・同時取得時のメモリと遅延を評価します。外部ノードは所有ハブ経由で取得します。

遠隔ソースは取得ごとに `HubCoordinator.Resolve` が一覧を探索します。健全なA→B→C／A→D→Cで探索予算が足りる場合、遠隔IDの解決1回に対して4本の探索RPCが生じます。リース失効や分岐停止を次の取得に反映するため、一覧はキャッシュしていません。[ソースの解決](../src/Hub/HubCoordinator.cs)・[探索の実装](../src/Hub/FederationNetwork.cs)

## 残る設計判断

1. **利用者認可・委譲・監査永続化**：後で設計する指定範囲。共有キーを知る相手はProviderApiやHubRelayApiを直接呼べる。ハブ経由の検証を強制するセキュリティ保証は未完成。相関IDは認証情報ではない。
2. **再起動・構成変更の承認単位**。復旧を各親ハブの検証で承認してよければ、その範囲を運用仕様に明記し、探索用に保持する起動識別子も直下の相手に絞れる。初回のDAG全体検証はこの案でも必要になる。入口が承認した世代だけを全経路で使う必要がある場合は、入口の検証済み識別子を下流へ伝え、各ホップで照合する設計が必要。4台で再現した挙動を参照。[状態と可用性](FEDERATION.md#状態と可用性)
3. **状態の永続化**：登録はメモリ内。永続化・水平分割は未実装。登録競合の照合対象は論理的な接続先であり、利用者／プロバイダの認証された所有権を保証する機構は後続の認可設計に含める。
4. **データ取得スキーマと負荷**：件数・バイト量の上限はあるがDBのCPU・ディスク消費を直接保証しない。ページング、増分取得、期間指定、時刻・単位・欠損の意味を別途設計する。JSONは先頭から、DBは直近行から逐次読むサンプル。
5. **運用上の接続**：外部プロバイダから登録先ハブへの登録接続と、所有ハブから外部ノードへの取得接続が必要。逆接続やトンネルは未実装。外部ノードIDとMSAサービス名には安定した一意の値を割り当てる。

CPU・ディスク監視は外部メトリクスURLに依存し、未設定時は固定間隔です。不正・欠落時には最大間隔を用います。複数プロバイダが同一DBへ与える合算負荷は制御していません。DAG探索は要求時に行うため、合流が多いと重複RPCが生じます。これらは後方互換性のための処理ではなく、現在の実装範囲の限界です。
